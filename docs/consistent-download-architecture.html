🏗️ Consistent Download Architecture

Designing a single, predictable, fast, and reliable download system for OpenKap

❌ Current System — 4 Inconsistent Paths

  • Bunny (encoding) → HTTP 202, user must retry manually
  • Bunny (ready) → signed redirect URL, 15-min expiry window
  • Local ≤5 min → ffmpeg blocks the HTTP request (sync)
  • Local >5 min → queued job, polls notifications every 8s

✅ Proposed System — 1 Unified Path

  • All videos → immediate HTTP 202 with a download token
  • All videos → background job converts & caches MP4
  • All videos → real-time SSE/WebSocket progress
  • All videos → same polling fallback, resumable downloads

🔴 Problem 1: Sync ffmpeg Blocks the Request Thread

Videos ≤ 5 minutes run convertToMp4Sync() inside the HTTP request. ffmpeg conversion can take 30-60 seconds for a 5-minute video. During this time:

• The PHP-FPM worker is tied up — reducing concurrency for other requests
• If the user closes the tab, CPU cycles are wasted
• No progress feedback — the browser just shows a spinner
• On slow servers, the request may hit PHP's max_execution_time and fail

Blocks request No progress Wastes CPU on cancel

🔴 Problem 2: Bunny Redirect URLs Expire

Bunny videos get a 15-minute signed proxy URL (temporarySignedRoute). If the user doesn't start the download within that window, the link is dead and they must re-request. The proxy endpoint (streamBunnyDownload) also streams the entire file through the app server, doubling bandwidth costs and adding latency.

15-min expiry Double bandwidth No retry

🔴 Problem 3: Polling Instead of Push

The useDownloadTracker composable polls GET /api/notifications every 8 seconds. This means:

• 0–8 second delay between job completion and user notification
• Unnecessary HTTP requests when no downloads are in progress
• The tracker can miss notifications if they're on page 2 of paginated results
• No way to show real-time conversion progress (e.g., "68% complete")

8s latency No progress % Pagination gaps

🔴 Problem 4: Files Deleted Immediately — No Caching

Both downloadMp4() and convertToMp4Sync() use deleteFileAfterSend(true). If the download fails mid-way (network blip, browser crash), the user must re-convert the entire video from scratch. There's no caching, no retry, and no resumption.

No caching No resume Re-convert on failure

🔴 Problem 5: No Download Token / Rate Limiting

The current endpoints have no per-download authorization. Anyone with a valid session can call GET /api/videos/{id}/download-mp4 repeatedly, triggering redundant conversions. There's no way to limit downloads per user, expire download links, or track download counts.

No per-download auth No rate limiting No download analytics

Unified Download Pipeline

Every video download follows the exact same path regardless of storage type (Bunny or Local) or duration.

1️⃣ User Clicks Download → POST /api/downloads
Single endpoint for all downloads. Payload: { video_id }. Returns immediately with { download_id, token, status: "queued" } — HTTP 202. Always async, never blocks.
2️⃣ DownloadManager::request(video, user)
• Creates a Download record: id, video_id, user_id, token (UUID), status, progress, format, file_path, file_size, expires_at, created_at
• Checks if a cached MP4 already exists → if yes, marks status = 'ready' immediately
• Dispatches ConvertVideoToMp4ForDownloadJob (same job for all videos)
• Returns the download token to the frontend
3️⃣ ConvertVideoToMp4ForDownloadJob (Background)
• Updates Download.status = 'converting' and progress incrementally
• For Bunny videos: downloads the MP4 renditions from Bunny CDN, remuxes locally
• For Local videos: runs the existing ffmpeg pipeline
• Emits SSE events at every 10% progress increment
• On success: saves to storage/app/downloads/{id}.mp4, marks status 'ready', sets expires_at = now + 24h
• On failure: marks status 'failed' with error message
4️⃣ Frontend Receives Real-Time Progress via SSE
• Opens an EventSource to GET /api/downloads/{id}/progress (SSE stream)
• Receives events: { progress: 45, status: "converting" }
• Updates UI in real-time: progress bar, percentage, estimated time remaining
• Falls back to polling GET /api/downloads/{id} every 5s if SSE fails
5️⃣ Download Ready → GET /api/downloads/{token}/file
• Token-based access — no session auth required (shareable, expiring)
• Supports Range headers for resumable downloads
• Streams the cached MP4 file directly
• File remains cached for 24 hours (configurable) — subsequent downloads are instant
• Records download completion for analytics

♻️ File Lifecycle & Caching

PhaseActionDetails
1. Request Check cache If a ready download exists for this video+format and hasn't expired, return the existing token immediately — zero conversion time
2. Convert Background job ffmpeg runs in a queue worker. Progress is emitted to a Redis pub/sub channel that the SSE endpoint listens to
3. Ready File cached MP4 stored at storage/app/downloads/{download_id}.mp4. Token is active for 24 hours
4. Download Stream to user Supports Range: bytes=0- for resumable downloads. File is NOT deleted after streaming
5. Expiry Scheduled cleanup A CleanupExpiredDownloads scheduled command runs hourly, deletes files and DB records past expires_at. If a new download is requested for the same video, step 1 reuses the cache

Phased Migration Plan

No breaking changes. New endpoints coexist with old ones during migration.

Phase 1: Foundation (Week 1)
• Create downloads table migration
• Create Download model, DownloadRepository, DownloadManager
• Create DownloadData DTO
• Add POST /api/downloads endpoint (returns { download_id, token, status })
• Add GET /api/downloads/{token} status check endpoint
• Deploy behind feature flag — existing endpoints unchanged
Phase 2: SSE & Progress (Week 2)
• Implement Redis pub/sub for conversion progress events
• Add GET /api/downloads/{id}/progress SSE endpoint
• Update ConvertVideoToMp4ForDownloadJob to emit progress events
• Create useDownloadProgress composable (replaces useDownloadTracker polling)
• Add progress bar UI component
Phase 3: Caching & Resumable Downloads (Week 3)
• Implement download file caching with 24h TTL
• Add GET /api/downloads/{token}/file with Range header support
• Add CleanupExpiredDownloads scheduled command
• Add cache-hit logic: reuse existing MP4 if still valid
• Update Bunny path to download once, cache locally
Phase 4: Frontend Migration (Week 4)
• Update VideoPlayerView.vue and VideosView.vue to use new endpoints
• Update NotificationBell.vue to use SSE-driven progress
• Add resumable download support in the UI
• Deprecate old endpoints (request-download-mp4, download-mp4, download-bunny)
• Remove old endpoints after 2-week deprecation window
